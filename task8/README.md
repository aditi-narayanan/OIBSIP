# Wireshark Network Traffic Capture and Analysis

## Overview

This project demonstrates network traffic capture using Wireshark, focusing on HTTPS traffic generated by a browser (likely Mozilla Firefox) during startup.

## Tools Used

- **Wireshark** for packet capture and filtering

## Steps Followed

1. Installed Wireshark on a Linux VM.
2. Captured traffic on the local network.
3. Applied filters in Wireshark to isolate HTTP-related traffic (TLS/HTTPS in modern cases).
4. Analyzed DNS queries, TCP handshakes, and TLS sessions.

## Observations

- **DNS Queries**: Domains like `contile.services.mozilla.com`, `example.org`, and `detectportal.firefox.com` were resolved via DNS (A and AAAA records).
- **TLS Handshakes**: Multiple TLS 1.3 handshakes initiated, with successful exchanges involving Client Hello, Server Hello, Change Cipher Spec, and encrypted Application Data.
- **Traffic Patterns**: All HTTP traffic was encrypted over TLS (port 443). No plaintext HTTP observed.
- **User Activity**: Likely Firefox browser performing background operations such as telemetry, update checks, and captive portal detection.

# Overall Analysis of Captured Packets

This packet capture represents a typical HTTPS-based communication session initiated by a client (`10.0.2.15`) using Mozilla Firefox or a similar browser. Below is a summarized analysis of the traffic captured:

---

## 1. DNS Resolution Phase

The capture begins with DNS queries initiated by the client:

### Domains Queried:
- `contile.services.mozilla.com`
- `content-signature-2.cdn.mozilla.net`
- `push.services.mozilla.com`
- `firefox.settings.services.mozilla.com`
- `example.org`
- `detectportal.firefox.com`
- `ipv4only.arpa`

- Both **A (IPv4)** and **AAAA (IPv6)** record lookups are performed.
- The DNS server responds with valid IP addresses and **CNAME redirections** for each domain.

---

## 2. HTTPS (TLS) Handshakes and Sessions

After successful DNS resolution, the client establishes **TLS 1.3 connections** to multiple destinations:

### Servers Contacted:
- `34.36.137.203` (Mozilla services)
- `34.107.243.93`, `34.149.100.209`, etc.

### TLS Handshake Steps Observed:
- `Client Hello` (includes Server Name Indication - **SNI**)
- `Server Hello` + `Change Cipher Spec`
- Encrypted Application Data exchange  
  (Note: Actual HTTP contents are **not visible** due to encryption)

These connections are likely for:
- Firefox telemetry  
- Update checking  
- Captive portal detection

---

## 3. Traffic Types and Protocols

| Protocol  | Packets Observed | Purpose                        |
|-----------|------------------|--------------------------------|
| DNS       | Many (UDP)       | Domain name resolution         |
| TCP       | Used for TLS     | Connection setup (SYN, ACK...) |
| TLSv1.3   | Many             | Encrypted HTTP-over-TLS data   |

- **No unencrypted HTTP traffic** observed — all web requests are **encrypted via HTTPS**.
- **Packet sizes** vary significantly:
  - DNS: mostly under 200 bytes  
  - TLS handshake and app data: can exceed 1 KB

---

## Likely User Activity

From the domains contacted, we can infer:

- The client is most likely **Firefox** initializing background network services.
- **No user-initiated browsing** is evident — all traffic appears automated/background:
  - Startup checks  
  - Update services  
- Query to `example.org` likely for **connectivity test** or **redirection handling**.

---

## Security and Privacy Notes

- **No suspicious activity or malicious traffic** is evident.
- The capture reflects **typical behavior of a browser startup sequence**.
- Usage of **TLS 1.3** indicates secure connections with modern encryption.

---


## Conclusion

The captured traffic reflects secure communication patterns typical of modern web browsers. DNS and TLS packet flows were successfully captured and analyzed.
